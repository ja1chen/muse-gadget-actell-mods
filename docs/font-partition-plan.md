# 保留现有数据的通用只读资源分区规划

状态：已生成并校验追加资源区的构建用 CSV，并接入[只读读取器和字体分页](caption-font-integration.md)。已完成设备核查与完整 Flash 私有备份；确认尾部旧应用和资源后，经用户明确授权覆盖字体包占用范围，已追加资源区并将独立字体固件写入非活动 OTA 槽、校验后切换启动。适用于固定 Muse SDK 的 Waveshare 2.16、16MiB Flash 配置。候选字库和容量证据见 [字体实施报告](caption-fonts.md)，实际二进制包与按体积分配预算见 [通用资源包](read-only-resources.md)。

## 可行性与布局

可采用只向未分配尾部追加分区的方式，保留全部既有分区的名称、类型、子类型、地址和大小，以及原来的分区表位置 `0x10000`。无需搬移 NVS、应用或产品参数。

| 区域 | 地址 | 大小 | 处理 |
|---|---|---|---|
| Bootloader 与分区表之前的空间 | `0x000000–0x00FFFF` | 64KiB | 保持原样 |
| 分区表扇区 | `0x010000–0x010FFF` | 4KiB | 只更新表，保留原条目并追加字体条目 |
| `nvs` | `0x011000` | 48KiB | 保持原样 |
| `otadata` | `0x01D000` | 8KiB | 迁移时不擦除、不重置 |
| `phy_init` | `0x01F000` | 4KiB | 保持原样 |
| `ota_0` | `0x020000` | 4MiB | 保留地址与容量 |
| `ota_1` | `0x420000` | 4MiB | 保留地址与容量 |
| `prod_data` | `0x820000` | 4KiB | 保持原样 |
| `prod_bak` | `0x821000` | 4KiB | 保持原样 |
| 对齐空隙 | `0x822000–0x82FFFF` | 56KiB | 保留，便于字体映射按 64KiB 对齐 |
| 新增 `actell_assets` | `0x830000–0xFFFFFF` | **7.8125MiB** | 字体、来源授权、后续图片与动画共享 |

拟追加 CSV 条目：`actell_assets, data, 0x40, 0x830000, 0x7D0000,`。自定义数据子类型须与当前完整工程核查无冲突。该空间是通用资源容量，不是字体独占。字体按实际包大小加约 10%（至少 256KiB、按 64KiB 对齐）升级预算，其余可用于其他资源。Regular 24px/4bpp 的实测包加余量后可留 1.5MiB 给其他资源；28px Medium 虽然包本身装得下，但加余量后超预算 128KiB。未选定最终字号字重。

源码分区表中未分配不代表真机该区域必然没有其他数据。执行前必须确认实机 Flash 容量、设备现有分区表和额外裸地址存储用途；不匹配即停止套用此布局。

当前只读核查发现，设备还保留位于 `0x8000` 的旧分区表，其布局与当前 `0x10000` 的 Muse 表不同：旧 `ota_0` 位于 `0x620000`，固件结构、校验和及 SHA-256 均有效，尾部跨入拟用资源区；旧 `assets` 位于 `0x920000`、容量 3MiB，是通过校验的旧版 mmap 资源包，含 24 项资源，其中 21 项为 PNG；旧 `storage` 位于 `0xC20000`、容量 3MiB，可识别为 SPIFFS，发现 3 个 MP3 文件头。当前 Muse 业务代码未发现对这些旧区域的访问；这支持旧固件资源残留的判断，但不能证明 MP3 全是出厂样本或允许删除。完整备份、结构报告和原始日志仅保存于 `local/credentials/`、`local/validation/` 和 `local/logs/`。本次经用户在用途核查后明确同意继续刷机，已覆盖资源包占用范围；旧应用也可能被新的非活动槽固件覆盖。原始内容仍在完整私有备份中。后续迁移同样不能将未登记区域视为空白。

## 保留数据的迁移步骤

1. 先在主机实现并测试资源包、字体读取和损坏回退；以新旧分区表完成构建校验。新固件遇到旧分区表、无资源、哈希不符或不兼容版本时，均回到原字体，不自动格式化或写资源。
2. 获得实际设备操作授权后，确认当前运行槽位、Flash 容量、分区表、加密/安全启动约束及应用版本。设备凭据不显示、不解析、不写进日志。
3. 在本机凭据目录保存受保护的必要原始备份：旧分区表、持久数据及恢复所需材料；文件权限 0600，仅记录校验摘要。若启用 Flash 加密，需另行验证备份与恢复方式，不能假定普通读回可直接恢复。
4. 首次资源部署先只写已确认可用的尾部资源区并核验；此时旧固件及旧分区表仍可运行。随后在稳定供电下更新 `0x10000` 的分区表扇区，保留所有既有条目。此扇区更新不具备应用双 OTA 的断电回滚保证，需准备 USB 恢复方式。
5. 通过保留的双 OTA 机制将兼容新旧分区表的新应用安装到非运行槽位并校验，再切换和确认新应用。具体更新命令根据当时设备启动状态生成，不能沿用默认向 `0x20000` 写应用的命令覆盖运行槽位。
6. 验证原 Wi-Fi、配对和设置仍存在，校验受保护区域在迁移写入阶段未被改变，再进行字体与交互验收。新应用启动后可能正常更新设置，不能要求整个 NVS 永远字节不变。

整个迁移不执行整片擦除、不写空 NVS、不写初始化 otadata、不更换 Bootloader、不清账号或触发重新配对。保留分区字节还需配合软件兼容：检查启动代码对 NVS 错误的擦除分支、设置 schema 迁移和凭据 namespace；首次升级不得因新增字体主动清理旧数据。保留数据是实施约束，不能仅靠 CSV 相同就宣称已验收。

## 资源格式、内存与升级

不能直接把现有 C 数组文件当作可映射资源。现已实现带完整性和版本检查的通用包、分区只读映射和有界逐字形解码，避免把数 MiB bitmap 复制进 RAM。LVGL 原二进制加载器会复制整个 bitmap，本实现不调用该整库加载路径。仍需测量真机 RAM、PSRAM、映射空间和耗时。

资源头记录格式版本、字族 profile、字集和字体度量、长度及哈希；所有偏移在资源分区内校验。普通哈希只证明完整性，不取代现有更新认证和签名信任机制。发布包随附 OFL、来源和生成记录。

当前布局只有一份共享字体，没有资源 A/B。它保留应用双 OTA，但不能承诺字体更新本身原子或可回滚。以后更新共享资源前需确认两个应用槽位均兼容；应用回滚遇到资源不兼容时使用内置原字体。中断写入也须回退原字体，不能阻止设备启动。若未来要求字体更新也具备 A/B，需要另行评估容量，不擅自缩减应用或 NVS。

## 验收与恢复

- 主机校验：原条目完全一致；无重叠；满足对齐、16MiB 容量和资源预算；分区表生成并反向解析一致。
- 软件校验：资源有效、缺失、截断、损坏、越界与版本不符；新应用在旧表下能安全回退；旧应用在新表下仍可启动；新字体开关和无屏构建。
- 首刷核查：资源包、分区表、非活动槽应用与 OTA 记录均通过读回比对；切换前 NVS、产品参数、PHY 数据、引导区域与保留的一份 OTA 记录逐字节一致。新固件在预期槽位启动，共享字体加载 29,137 字形、行高 46，未回退；45 秒观察无崩溃或看门狗异常，连接状态报告仅保存在本机验证目录。详细证据仅在 `local/validation/caption-flash/`。
- 待真机验收：应用 OTA 回滚、字体损坏回退、显示/分页/动画、连续更新内存与帧耗时；启动通过不等于这些项目已通过。
- 恢复：优先回滚应用并使用原字体；需要恢复旧表时只恢复原表扇区。既有分区地址未变，字体尾部可保留闲置。设备断电或安全配置异常后的恢复必须基于已核实备份与设备状态，不能承诺无条件无损恢复。
